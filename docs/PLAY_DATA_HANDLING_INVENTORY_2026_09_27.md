# Play data-handling inventory — 27 September 2026

This is a source-based inventory for the privacy policy, account-deletion procedure and Google Play Data safety review. It is **not a completed Console declaration or proof of deployed configuration**. The inspected source snapshot is `c76cfa38ffdf`; later policy/UI work must be checked against the final signed candidate. No production records, credentials, personal device identifiers or raw diagnostic exports were used. No tests, builds, cloud mutations or device actions were performed for this inventory.

The app processes identifiable workplace records. Calling it an offline app, an account-free app, or an app that collects no personal data would be inaccurate. Google sign-in creates an app profile even before an administrator approves access.

## SDK behavior beyond app fields

Firebase’s [Android disclosure reference](https://firebase.google.com/docs/android/play-data-disclosure) additionally describes Authentication/Functions IP and request metadata, Firestore/Functions authenticated UID transmission, and Crashlytics crash state, device metadata, installation UUID and Sessions/Installations dependencies. App Check uses attestation tokens when enabled. Firebase documents HTTPS transport and service-provider/subprocessor handling. Include these SDK flows when completing the form; a small app schema does not imply small SDK collection.

The repository integrates Auth, Firestore, Functions, Messaging, Crashlytics and App Check. It has no explicit Firebase Analytics, Firebase Storage or advertising SDK dependency in the inspected `pubspec.yaml`/lockfile. A `firebase_analytics_collection_enabled` manifest entry alone is not proof that Analytics is installed. Verify the **resolved Android dependencies and merged manifest of the final artifact**, including transitive SDKs. No camera, microphone, contacts, SMS, GPS/location or health/financial collection feature was found in the inspected source. This is not a claim that free-text operational submissions cannot contain such information.

Use Firebase’s [privacy and security documentation](https://firebase.google.com/support/privacy) for provider-specific processing/retention, and the actual service configuration for this project. This inventory makes no promise that all data expires after a single number of days.

## Permissions, transport and local storage

- The main Android manifest explicitly requests `POST_NOTIFICATIONS` and `VIBRATE`. A **saved package-proof release manifest dated 21 September** also contains `INTERNET`, `ACCESS_NETWORK_STATE`, `WAKE_LOCK`, `com.google.android.c2dm.permission.RECEIVE`, `READ_GSERVICES` and an app-scoped protected receiver permission. That saved artifact has collection disabled and is not proof of final production collection settings. No new package was built for this review.
- Production Gradle normally enables Firebase collection/init placeholders; only the CI package-proof switch disables them. [Gradle](../android/app/build.gradle.kts#L88). Release `AppLogger.init` separately enables Crashlytics. A CI artifact or DEV emulator session cannot substantiate a “no collection” production declaration.
- The app uses Firebase-managed network transports. Emulator HTTP is isolated by the DEV configuration; it is not the intended production transport. No application-level end-to-end encryption implementation was found. Do not describe ordinary Firebase transport encryption as end-to-end encryption.
- Isar opens in the application documents directory with no app-supplied encryption setting in this path. It holds downloaded business data and unsent/uncertain work. Shared preferences hold installation IDs, synchronization/provenance state and some retained request journals. Firebase SDK caches/authentication state are additional local stores. [Database open](../lib/main.dart#L136), [request journal](../lib/core/persistence/request_identity_journal.dart).
- `allowBackup=false` and explicit exclusions cover app root/files/databases/preferences/external data for Android cloud backup and device transfer. [Manifest](../android/app/src/main/AndroidManifest.xml), [backup rules](../android/app/src/main/res/xml/backup_rules.xml), [transfer rules](../android/app/src/main/res/xml/data_extraction_rules.xml). This does not erase explicit report exports or authorized recovery copies.
- Google profile images are requested from their stored URL host. PDFs may leave through a chosen print/share provider. Local diagnostic text can be copied to the clipboard. Those destinations are not governed by Firestore reading permissions after export.

## Retention mechanisms are specific, not universal

1. **Most operational, user and audit records:** no general timed deletion policy appears in source. Closure, archive, access revocation and soft deletion are different from erasure.
2. **Morning Review:** the source contains a 14-day retention constant and `expiresAt` TTL declarations for selected collections. Open newer meetings retain content with null expiry; unfinished concerns/actions and minimal exact-request acceptance can outlive display/document retention. Therefore “all meeting data is deleted after 14 days” would be false. Confirm deployed TTL policies separately. [Mutation/receipt rules](../functions/src/morningReviewMutation.ts#L182), [population protection](../functions/src/morningReviewRetention.ts), [TTL configuration](../firestore.indexes.json#L1106).
3. **Quality monitoring:** the scheduled process changes due closed records from recent to archived. It does not delete the record. [Archive planner](../functions/src/qualityMonitoringRetention.ts#L46), [scheduled invocation](../functions/src/maintenanceWorkflow/escalationSweep.ts#L198).
4. **Pilot permanent purge:** the governed source restricts this to maintenance records, directives and legacy job templates, with dependency checks and retained purge evidence. It is not account deletion, does not cover all personal data and is not a general privacy-request procedure. [Purge scope](../functions/src/pilotRecordPurge.ts#L13).
5. **Local recovery/discard:** targeted recovery can preserve raw database backups and refuse loss of uncertain submissions. Clearing a local queue/cache is not server deletion. Signing out deliberately preserves business records and retained request evidence.

## Decisions and verification needed before final declarations

- **Operational account-deletion fulfillment:** the inspected snapshot has sign-out and authority revocation, but no Firebase Auth account deletion, profile deletion or cross-record privacy-request workflow. The public request pages and in-app link are separate from backend erasure; they must lead to an actual monitored procedure. Specify identity verification, account/profile/token removal, treatment of other devices/caches, exported copies, and any justified retention of shared evidence. Do not promise immediate or complete deletion that the procedure cannot deliver.
- **Retention ownership:** choose and document supported retention/deletion rules for profiles, work content, audits/receipts, security logs and recovery exports. Preserve required integrity through a reviewed process; do not silently rewrite historic actors or treat every record as automatically exempt.
- **Public policy wording:** identify Google/Firebase as service providers and describe role-based workplace visibility, notification content and user-initiated exports. Do not automatically translate “uses a service provider” into either “sold” or “no sharing”; apply the current Play definitions to the actual configuration and use.
- **Final candidate verification:** confirm production SDK versions, collection flags, notification behavior, network/image destinations, App Check activation/enforcement, provider retention configuration and Android permissions. The source default for client App Check and the mutating-callable enforcement parameter is false; inclusion of the provider does not establish current production enforcement. [Client gate](../lib/core/security/app_check_bootstrap.dart#L4), [server gate](../functions/src/callableSecurityConfig.ts#L8).
- **Disclosure accuracy:** likely categories include name, email, user IDs, device/other IDs, crash logs/diagnostics and attributed user-generated operational content. Confirm the profile-image and exported-document mapping in the current Console form. State conditional collection accurately: optional notification display is not equivalent to optional token collection; a profile photo being nullable is not an in-app opt-out; crash UID hashing does not remove all identifying SDK data.

This inventory supports preparation of truthful disclosures. It does not certify a published privacy policy, an exercised deletion request, a final signed artifact, a production deployment or Play approval.
