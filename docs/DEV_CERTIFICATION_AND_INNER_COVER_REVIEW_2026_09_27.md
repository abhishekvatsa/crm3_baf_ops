## Catalogue assessment and execution scope

All **492 scenarios across 36 domains** were assessed for legitimacy, business-policy assumptions and overlap with existing tests. That assessment was not an execution of all 492 scenarios. Catalogue priorities are planning priorities, not a count of discovered defects; existing automated test totals cannot be converted into a catalogue completion percentage.

The catalogue remains useful with explicit distinctions: operation-specific roles, physical closure versus nonblocking follow-up, ordinary agency completion versus authorised supervisor resolution, supported legacy compatibility versus new assignment routes, and recorded time versus physical event time. Proposed outcomes that differ from an established business contract require an explicit policy decision rather than an automatic code change.

This phase added targeted proof where the existing Android and HTTP planned-work journey was explicitly **No RED**, strengthened unattended business journeys, and checked the source against strict client readers. ## Inner Cover dates, history and presentation

- Calendar selection and typed entry now agree on **`dd-MM-yyyy`**; displayed times use **`dd-MM-yyyy HH:mm`**. Typed input is strict, including invalid dates and leap years. The change preserves UTC command serialization, existing device-local UI conversion and the PDF's explicit plant-time conversion.
- A future physical event time remains the user's visible selection and is rejected until corrected. It is no longer silently replaced with the current time. Inspection, physical occurrence and recording times retain their distinct meanings.
- History reads now carry rejected-record, cache and pending-write evidence. Only a complete, server-confirmed empty result can state that no assignment was recorded. Partial, cached, failed and refreshing history remain visibly qualified; readable retained entries survive errors, and changing the subject clears retained history.
- History cards distinguish pairing recorded time from physical removal and removal recorded time. The Base/Inner Cover PDF uses the same date style and labels pairing as recorded evidence rather than asserting an independently observed installation time.
- Summary filters can scroll within a bounded area, tabs adapt to narrow screens, and detail labels stack when width or text size requires it. Focused widget checks include 320-pixel width with enlarged text. Read-only inspection of the normal DEV phone covered Bases, Pool, cover details, linkage and removal history; screenshots are retained privately. Opening those views is visual evidence, not a new lifecycle mutation or release-device qualification.

Independent source review found no additional confirmed blocker in these client/UI/repository/PDF changes. Specific limits remain: pairing/replacement dialogs with the keyboard open are outside the new narrow-screen checks, and Base history now builds all displayed history cards eagerly, so large-history scrolling performance is not certified by the small fixtures.
