# Build 28 client/backend compatibility advisory — 12 September 2026

**Decision: the candidate is not a transparent backend-only upgrade for every installed user.** Most changes preserve the old request and response contracts, and the timestamp repairs specifically help installed clients. However, the inspection-finding adjudication change requires a field that both verified Build 21 and Build 27 clients omit. The complete candidate backend therefore needs an explicit cutover plan for people who adjudicate findings. Conversely, the new client's adjudication, campaign reopening and plan revalidation cannot all run against the recorded deployed backend.

This is a read-only source and release-evidence assessment, not a deployment approval, live Firebase check, physical-device test or claim that Build 28 exists. It does not authorize changes to operational data or frozen pending commands.

Comparing `c00` with the reviewed working tree changes ten Functions source files: asset registry, Inner Cover lifecycle, burner lifecycle, workflow envelope, dispatcher, idempotency, inspection campaign, inspection evidence, maintenance plan and the memory store. The memory store serves host tests. The production behavior reaches three existing callable names:

Export-file equality does not mean all exported behavior is unchanged: shared helpers have the three callers above. Any deployment command must use the final assessed dependency scope.

## Receipt and persisted-data compatibility

The new receipt evidence is stored server-side, not added to the callable success response. This distinction matters because old Dart response decoders enforce exact top-level key sets.

* Workflow success still has exactly `commandId`, `resultKey`, `aggregateVersion`, `result`, `appliedAt`. Persisted `receiptSchemaVersion` stays **2**, with the existing full-envelope `sha256:` fingerprint and actor/authority binding. Adjudication adds `findingVersion` inside the result object, which the old generic result decoder accepts. This does not solve its missing request field.
* Inner Cover success still has `ok`, `requestId`, `operation`, `innerCoverId`, `version`, `secondaryVersion`, `auditId`, `committedAt`, `idempotentReplay`. Stored receipt schema stays **1**; **new** fingerprints use `innercover3-sha256:`, and receipt/audit retain exact timestamp strings and audit evidence digest. Legacy `innercover1`/`innercover2` fingerprints are used only to check historical receipts. Six-digit requests have no historical accepted fingerprint because that old parser could not accept them.
* Registry success still has `ok`, `requestId`, `operation`, `assetClassId`, `nodeId`, `version`, `auditId`, `committedAt`, `idempotentReplay`. Stored receipt schema stays **1**; candidate **new** fingerprints use `assetreg4-sha256:`. Historical `assetreg1`/`assetreg2`/`assetreg3` retain their old calculation only for receipt comparison, with immutable audit date verification. Replacement verifies both relevant audit outcomes.
* Public timestamps remain canonical UTC milliseconds. Exact microsecond command evidence is retained separately; this change does not increase timestamp precision of all existing profile fields or rewrite historical records.
* Campaign and maintenance-plan schemas remain **2**. Inspected old decoders select known fields rather than rejecting the new top-level history/review fields. Campaign reopening reuses existing `open`, not an unknown enum value. Plan review retains `ready`, physical identity and maintenance definition.
* Once new fingerprints or reopened campaign histories have been written, restoring the `c00` binary is not a complete safe rollback. Preserve the new readers/invariants in a forward fix or a specifically tested compatibility rollback. Never relabel new receipts as old or erase receipt/audit history.

## Already deployed versus newly proposed

There are four Functions source differences between the finalized Build 27 source and `c00`: asset-condition replay, operational-event behavior, morning-review handling and callable abuse control. They are part of the recorded deployed baseline, not newly introduced by the current candidate. Among them, operational-event `expectedActorUid` is optional and does not force an old client to add a field; stored accepted/rejected outcomes and replay checks changed. Morning review retains its request keys and expands/fixes governed content handling. This advisory does not retroactively claim those prior deployments were fully exercised on every installed version.

The targeted timestamp audit found no equivalent current three-versus-six-digit rejection in hierarchy (no client date field), condition's nested event evidence (allows up to six fractions), or workflow ticket/inspection/plan parsers (accept and canonicalize). Morning-review and operational-event client serializers already emitted milliseconds in the verified old source. Strict server-authored receipt checks should not be globally relaxed. Permissive date parsing and millisecond chronology elsewhere are separate hardening questions.

## Recommended rollout decision

1. **Do not approve an unqualified backend-only rollout of the entire candidate.** First identify the people/devices permitted to adjudicate findings and bind the exact successor artifact to a coordinated upgrade window. Communicate that old adjudication must not be used during the gap. Other old-client functions need not be broadly disabled solely because of this one field change.
2. Freeze and verify the final backend and client together, including actual old-client command fixtures against the candidate backend, current-client response decoding, accepted old adjudication replay, and an unaccepted old adjudication refusal. The registry extension and final reopen chronology guard need the final source's checks; earlier test totals do not certify later edits.
3. Deploy the assessed backend dependency scope, perform its strict readback, then use the new actions only on the exact upgraded client. Do not distribute the new client into ordinary use against `c00` and assume its new actions will work. A short controlled action outage may be needed because neither order gives transparent adjudication compatibility.
4. If a mixed-version interval with uninterrupted adjudication is required, stop and design a separate, explicit compatibility protocol. The old request lacks the finding revision its operator reviewed. Filling `expectedFindingVersion` from the current server document, dropping the fence, or trusting the campaign version would recreate the defect. A truthful adapter may return an update/review-required result; it cannot silently manufacture that missing evidence. Such an adapter/capability gate is **not implemented by this advisory**.
5. Preserve old pending command ID, actor and bytes. A valid accepted command should replay exactly. A never-accepted adjudication without the reviewed finding version must be resolved through a fresh, explicit review after acceptance status is established; do not mutate the old envelope or blindly create a second mutation.
6. Before pilot expansion, exercise one old-client-compatible path and the repaired new paths on the exact deployed backend/APK combination. Include inspection adjudication, reopen → later same-finding verification, plan review → separately completed maintenance, acceptance → linkage → original retry, component replacement, and relevant completion evidence. Host/emulator green results support this decision but do not replace those exact-artifact checks.

No command-level minimum-version or capability negotiation was found in the inspected workflow call path. `getBackendReleaseIdentity` is used by diagnostics; it is not an existing automatic gate for adjudication/revalidation/reopening. The rollout must therefore make the cutover concrete, or implement and test a narrow capability mechanism before relying on one.
