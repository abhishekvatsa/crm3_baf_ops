# 70I-B2 — Permanent Identity, Signing and O-01–O-05 Closure Runbook

## Purpose

This runbook governs the transition from the verification-only B1 artifact to a
permanently identified, production-signed, independently verified pre-release
artifact. It closes O-01 through O-05 only within the boundaries stated below.

It does not authorize unrestricted plant release and does not deploy Firestore
Rules, indexes or Cloud Functions.

## Governing boundaries

- **O-01** closes when the corrected 70I-C parity result is encoded in the
  backend authority, B1 builder, verifier, runbook and contract test.
- **O-02** closes for permanent Android/Firebase source and artifact identity.
  Device-by-device migration, local-state reconciliation and retirement of the
  placeholder package remain O-10/70J.
- **O-03** closes only for a pre-existing approved signer with separately
  evidenced primary custody, backup custody and recovery proof.
- **O-04** closes only when the source policy is merged and the build number is
  atomically consumed by a remote reservation tag, followed by a built tag
  after independent verification and dual custody. Failed and withdrawn builds
  still consume the number.
- **O-05** closes as a production-signed, independently verified,
  non-distributable pre-release artifact. Any controlled-pilot distribution
  requires a separate post-build approval bound to the exact package hash.

## Non-negotiable controls

1. No production key is generated by repository tooling.
2. No password, keystore, service-account JSON or operational database enters
   Git, the evidence package or chat.
3. Source must begin at the named live baseline and remain reviewable through
   four narrow commits in one PR.
4. Production artifacts are built only after merge from exact live remote main
   by the protected production workflow.
5. Build numbers are never reused. A remote reservation tag is created before
   the build and remains authoritative after failure or withdrawal.
6. Firebase CLI, GitHub Actions, bundletool and Linux Isar native core are
   version/hash governed.
7. APK and AAB identities, signatures, signer certificate and debuggable state
   are independently verified.
8. AAB strict verification uses a temporary truststore containing only the
   approved public signing certificate.
9. The governed package and closure package require mandatory SHA-256 sidecars
   and two distinct long-term custody roots.
10. Promotion never rebuilds the artifact.

## One-go campaign sequence

### Phase A — external authorities

Prepare and approve:

- permanent `applicationId` and `namespace`;
- public version and monotonic build-number policy;
- pre-existing keystore and certificate fingerprints;
- primary/backup/recovery custody evidence;
- Firebase Android app registration for the permanent package and signer SHA-1;
- completed Android identity migration classification;
- approved bundletool hash;
- independently approved Linux x64 Isar-core hash, captured before the candidate build with `Capture_Linux_Isar_Core_Authority.ps1` or equivalent approved evidence;
- exact GitHub production environment and repository.

### Phase B — preparation branch

Run `Invoke_CRM_III_BAF_Ops_O1_O5_Governed_Campaign_v4.ps1` from clean live
main. It creates four commits:

1. corrected 70I-C provenance integration;
2. permanent Android/Firebase identity, source build-number reservation and
   migration-plan receipt;
3. fail-closed release signing and production policy;
4. production builder/verifier/workflow, pinned toolchain and contract tests.

The preparation phase does not build a production artifact, reserve a remote
number, push, merge, or deploy Firebase. Branch push is always a separate reviewed human action.

### Phase C — review and merge

Review every commit and the generated preparation evidence. Push the feature
branch manually, open one PR, require normal CI and merge to `main`. The PR
must contain exactly the four governed commit headlines; the finalizer verifies
that sequence from GitHub. Preserve the commits on main where repository policy
allows it.

### Phase D — protected one-time build

Dispatch `.github/workflows/production-artifact.yml` with the exact merged-main
commit, release ID, reservation ID and build number.

The workflow:

- confirms the commit is exact live remote main;
- verifies the merged production policy;
- atomically creates the annotated remote reservation tag;
- refuses an already-reserved or already-built number;
- restores pinned dependencies and Firebase CLI;
- verifies the approved Linux Isar core;
- restores the production keystore only from the protected environment;
- runs all mandatory gates;
- builds once and emits package plus mandatory sidecar.

A failed run consumes the number. Fix the cause, approve a new build number and
create a new policy/ledger commit before another production build.

### Phase E — independent finalization and dual custody

Run `Finalize_CRM_III_BAF_Ops_O1_O5_Closure_v4.ps1` with the exact GitHub run
ID and PR number. It queries GitHub itself, downloads the named run artifact,
re-verifies the package, checks the remote reservation tag, establishes two
independent custody copies, creates the built tag, creates a closure ZIP and
establishes dual custody for the closure evidence.

### Phase F — optional controlled-pilot promotion

After target-device migration/cutover evidence exists and an accountable
approver has accepted every named residual risk, use
`Create_Controlled_Pilot_Promotion_v4.ps1`. The promotion record is bound to
the exact package, manifest, APK, AAB, signer, commit, run, closure and custody
hashes. The artifact is not rebuilt. Approval and target-device records remain
in their governed external custody locations; the promotion package retains
only their references and SHA-256 values by default.

## Stop conditions

Stop immediately and preserve evidence on any:

- baseline, tree, source-archive or approval hash mismatch;
- reused/reserved build number;
- unexpected changed path;
- package/certificate/Firebase mismatch;
- test, emulator, signing, identity or native-core failure;
- missing sidecar;
- custody-copy mismatch;
- evidence loss, duplicate, unresolved rejection or false success.

Never clear app data or uninstall the placeholder application to conceal a
migration defect.
