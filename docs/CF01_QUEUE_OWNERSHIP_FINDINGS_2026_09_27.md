# CF-01: retained generic queue ownership

Status: **OPEN — release blocker**. This source review supports a draft PR for review, not merge, release, deployment, or distribution approval. No production records were read or changed for this review.

The current run guard prevents synchronization from continuing after its authenticated session changes, loses authority, or is disposed. It does not establish which account originally saved every older dirty Isar row. If account A saves work, synchronization never reaches the server, and account B later begins a new approved session, B is the current run owner. A separate durable mutation origin is necessary to decide whether B may send A's saved intent.

The finding is bounded to the permitted paths below. It is not a claim that every local queue lacks actor protection. These are source-verified counterexamples; an authenticated cross-account emulator reproduction has not yet been run for CF-01.

## Protections that remain effective

- `SyncService.syncAll` (`sync_service.dart:334`) installs a guard for the current run. Production supplies the stronger session/authority epoch guard; the standalone fallback pins the current Firebase UID. A changed session aborts subsequent guarded work. This is distinct from binding a row that predates the run.
- `_recordsEligibleForAutomaticPush` (`sync_service.push_infrastructure.dart:303`) honors retained permanent holds and refuses to send when the hold store is unreadable. It is not a row-origin migration or ownership proof.
- Maintenance creation, reopening, closure and withdrawal have explicit original-actor/retained-command checks. Governed template package/version writes carry actor-bound fields checked by Rules; publication audit creation binds the performer. These are not included in the three counterexamples.
- Job execution creation binds `assignedByUid` to current auth (`firestore.rules:482`); governed assignment uses its server command. Completion additionally checks the saved closing actor in `sync_service.executions.dart:539`. The counterexample is only the existing job's permitted work-field update.
- Diary creation/update binds `createdByUid`/`updatedByUid` and atomic audit evidence to current auth (`firestore.rules:919`–`975`). Module work/submission/acceptance/reopen/not-applicable transitions bind their relevant saved actor (`firestore.rules:770`–`826`). Sending another account's unchanged payload is refused by these server boundaries; a failed attempt is not evidence of successful replay.
- Ordinary directives use retained origin-bound commands. Unbound older ordinary directive rows are held rather than automatically uploaded (`sync_service.directives_abnormalities.dart:107`). Burner directive lifecycle protections are separate and remain in force.
- Charge-abnormality creation verifies both saved reporter and updater against the authenticated actor (`functions/src/chargeAbnormalityMutation.ts:2199`). Existing accepted mutation receipts also bind the actor. These facts do **not** establish durable origin for every unsubmitted legacy privileged update; that path still needs an explicit migration/review decision before claiming complete coverage.
- Standard audit Rules require `performedByUid == request.auth.uid` (`firestore.rules:3805`); failed cross-account audit writes are not silently reassigned. The knowledge sync path now reconciles identical accepted server evidence rather than sending a generic local-row write.

## Safe repair and evidence required

1. Bind every new mutation in the three affected paths to an immutable, durably saved original account before enqueueing or dispatch. Bind request identity, intended payload/version and project scope as appropriate. Enforce that origin in both dispatch/retry and the authoritative server boundary; a current-session check alone is insufficient.
2. Retain legacy rows without trustworthy origin for explicit review. Do not infer an editor from the currently signed-in account, a template creator, an execution assigner, a clock, or a new sync attempt. Preserve original payloads and history; do not silently delete, acknowledge, reattribute or resend them.
3. Keep exact accepted-receipt reconciliation separate from dispatch. Reading and adopting an already accepted identical server result must not create fresh intent or grant another actor permission to mutate it.
4. Add native Isar plus authenticated emulator tests: A saves offline; sign out; B with the same role signs in; B cannot send or acknowledge A's pending mutation; process restart retains that refusal; A can resume once; revocation/regrant and an interrupted receipt retain identity; legacy unbound rows remain reviewable; actual version conflicts preserve both evidence and local work. Include negative role and mismatched payload/project tests.
5. Update migration, governed decoder inventories and user-facing recovery only after those tests pass. The current commit/push must leave CF-01 explicitly open rather than changing release authority to conceal it.

No queue schema or ownership migration was introduced by this review.
