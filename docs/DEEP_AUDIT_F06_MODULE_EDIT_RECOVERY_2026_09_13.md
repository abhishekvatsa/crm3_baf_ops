# F06: native module edit conflict protection

This repair addresses the stale local module save described in the independent deep audit. It does not establish a whole-application outbox, replacement-device recovery, or physical-device crash durability.

## Save boundary

The editor captures `JobModuleSaveBaseline` before awaiting its input flow. A complete native clone preserves local linkage, raw metadata, and lane fields; it does not normalize them through the Firestore decoder. Inside the Isar write transaction, the repository compares the current local ID, revision and complete persisted preimage with that baseline. It also checks the current module's editable lifecycle, immutable/governed fields, and the uniquely identified current parent's open lifecycle. A missing local row is not treated as a new creation.

A successful update increments the matching current revision. A conflict leaves that row unchanged and atomically records the reviewed preimage, current row and attempted draft. The typed conflict is thrown only after that evidence transaction commits. If the evidence collection cannot be written, the business mutation remains refused and the application must not claim that the draft was durably saved.

## Evidence and recovery

The existing `AuditEvent` schema stores explicit conflict events under `planned_job_module_edit_conflict`, with evidence parts under `planned_job_module_edit_conflict_part`. The actual editing actor owns both. A manifest records a SHA-256 digest and chunk count; base64 chunks of at most 12,000 characters keep each JSON audit payload below the existing 20,000-character Firestore Rules limit without truncating draft contents. These are ordinary immutable audit events, eligible for the existing audit retry mechanism. They do not assert a successful business mutation or a server command origin. No schema or Rules change is introduced.

The native module workspace has a **Saved drafts** entry. Reads filter by the current actor before decoding contents and require complete, matching evidence. The review shows current work beside the saved draft. Restoring requires explicit confirmation that the saved responses, component actions, notes and progress will replace those work fields. It uses a freshly read module baseline and repeats the transaction checks. Identity, template, authority and lifecycle history fields are not restored from the losing draft. Closed modules/jobs remain reviewable but cannot be edited through this route.

The original conflict is retained after restoration. A separate `planned_job_module_edit_conflict_resolved` audit records the reviewed restoration in the same transaction as the module change. Account approval, identity and discipline permission are rechecked around the new recovery interface's awaited operations; an account change during its local write rolls back the transaction. The review does not rely on remote audit availability or grant general audit access to the editor.
